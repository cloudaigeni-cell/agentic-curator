Five storeys: work flows down, results flow up

How to read every plate

  1. Storey 4 plans. The orchestrator and the bus never touch a file.
  2. Storey 3 does one job per agent. Only the red one may remove anything.
  3. Storey 2 holds memory, rules, the model and the MCP client.
  4. Storey 1 is the protocol boundary: one MCP server, eight tools.
  5. Storey 0 is your library. Nothing reaches it except through storey 1.

Plate A · before any agent runs

Where everything lives on your machine

Steps

  1. Windows hosts WSL. Install Ubuntu once with wsl --install -d Ubuntu.
  2. Ubuntu holds the repository and a Python 3.11+ virtual environment.
  3. curator is the command you run. It starts the MCP server as a child process and talks to it over stdio.
  4. The library is any folder: ~/library, a Windows path under /mnt/c, or Drive for desktop mounted at /mnt/g.
  5. The LLM API is optional. With no key the offline provider answers.
# inside Ubuntu
sudo apt install -y python3-venv git
cd agentic-curator
python3 -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
curator doctor
You should see: Python, MCP SDK, Pillow and pypdf all OK, and "offline always available".
Plate B · runtime.py

Wiring: seven agents on one bus, one MCP handshake

Steps

  1. build_runtime() creates the five shared services: tracer, blackboard, policy gate, LLM provider, MCP client.
  2. Each agent registers the task kinds it handles. Two agents claiming one kind is an error at startup.
  3. Year and document agents register as factories, so every task gets a fresh instance.
  4. The MCP client launches the server, sends initialize, then tools/list, and learns the eight tools.

Phase 0 · scope

One MCP call inventories the library

Steps

  1. The orchestrator asks the MCP client to call list_items.
  2. The server walks the library and returns path, size, kind and a year for each file.
  3. Year comes from the filename first (IMG_20190704…, report_2021), then the modified time.
  4. The orchestrator sorts the 18 items into four piles, one per year.

Phase 1 · fan out

One subagent per year, running at the same time

Steps

  1. The orchestrator creates four year.analyse tasks, each carrying its own slice of files.
  2. bus.gather() runs them concurrently, up to four in flight.
  3. Each year agent calls hash_item for its files and gets a SHA-256 back.
  4. Each writes its records and a summary to the blackboard. No agent sees another year.

Phase 2 · read

Text and PDF: code proposes, the model may refine, code checks

Steps

  1. A document agent per year calls read_text. The server parses PDFs with pypdf.
  2. Code derives a subject key from the filename: years, months and "copy/v2" are stripped.
  3. If a model is configured it is asked for a better key, with the code's answer as fallback.
  4. The answer is checked (2 to 60 characters) before it is stored.
  5. Texts and subjects go to the blackboard for phases 3 and 5.

Phase 3 · compare

Duplicate documents: proof on one lane, judgement on the other

Steps

  1. Lane 1, identical bytes. Files sharing a SHA-256 form a group. The oldest stays; the rest become a delete proposal at confidence 1.00.
  2. Lane 2, similar text. Texts are cut into 5-word shingles and compared by Jaccard similarity.
  3. At 0.80 or more the pair becomes a merge candidate, never a delete: similar is a judgement, not a proof.
  4. Both lanes file proposals with their evidence on the blackboard. Nothing is removed.

Phase 4 · photos

Duplicate photos: 64 bits and three distance bands

Steps

  1. The photo finder calls image_signature. The server shrinks the image to 9×8 grey pixels.
  2. Each pixel is compared with its right-hand neighbour: 64 yes/no answers, the dHash.
  3. Two photos are compared by how many of the 64 bits differ.
  4. 0 to 4 bits: the same shot, re-saved or resized. Keep the largest, propose deleting the rest.
  5. 5 to 10 bits: the same scene a moment later. Sent to a human, never to the trash.

Phase 5 · merge

Consolidate: write, read back, verify, then propose

Steps

  1. Text files with the same subject key are grouped. PDFs and files already proven identical are left out.
  2. The consolidator writes one file per subject into curated/, each section headed with its source path, size and date.
  3. It reads the new file back through MCP.
  4. It verifies the opening of every source appears in it.
  5. Only if all sources are found does it propose retiring them. One miss and nothing is proposed.

Phase 6 · vet

The policy gate: four checks, then a token

Steps

  1. Eight proposals arrive from three agents: 6 deletes, 1 merge, 1 review.
  2. Each delete must pass four checks: confidence at least 0.90, no protected path, a named survivor, batch of 50 or fewer.
  3. Merge and review proposals are held for a human.
  4. The approved deletes are hashed into an approval token. Change one path and the token changes.
  5. A dry run stops here and writes plan.json.

Phase 7 · act (only with --execute)

Execute: token check, move to trash, undo if needed

Steps

  1. --execute turns dry-run off and dispatches delete.execute with the token.
  2. The deletion agent asks the policy to authorise: the token must match the plan as it stands now.
  3. It re-checks every path for protection and never touches the survivor.
  4. It calls move_to_trash. The server has no delete tool to call instead.
  5. Each move is written to manifest.jsonl. curator restore reads it and puts everything back.

[mcp]    deletion-agent -> library.move_to_trash  path=downloads/invoice_2019_march (1).txt
[policy] moved 8 file(s) to trash, refused 0

Plate 8 · after the run

What a run leaves behind

Read them in this order

  1. report.md: what was found, what is proposed, what was blocked.
  2. plan.json: every proposal with its evidence and the approval token. Review this before --execute.
  3. trace.jsonl: every event, in order. The file to open when something surprises you.
  4. blackboard.json: shared memory and who wrote each entry.
  5. summary.json: the numbers, for scripts.
cat runs/*/report.md
grep '"channel": "policy"' runs/*/trace.jsonl
A second run after executing finds 0 files to retire. If it finds more, read the trace before approving.

Practise on it

Watch

curator demo, then count the year- lines in the trace. Plates 0 and 1.

Speak MCP

curator tools --library demo_library, then call hash_item from ten lines of Python. Plate B.

Break the sandbox

Ask read_text for ../../etc/passwd. It must fail.

Tamper with a plan

Weaken plan_token() and watch test_changed_plan fail. Plate 6.

Add an agent

A LargeFileAgent on kind review.large. Register it; nothing else changes.

Add a model

Set CURATOR_PROVIDER and a key. The delete plan should not change. Plate 2.
